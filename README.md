# Решение

## Задание 1.
1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

Рекомендуемая СУБД: Реляционная (SQL) СУБД.Конкретные примеры: PostgreSQL, Microsoft SQL Server, Oracle Database.

Почему?
- Чёткая структура и целостность данных: Это ключевое требование. Реляционные СУБД основаны на строгой схеме данных (таблицы, столбцы, типы данных), что исключает возможность сохранения некорректной информации. Поддержка транзакций (ACID) гарантирует, что все финансовые операции будут либо полностью завершены, либо полностью отменены, предотвращая ситуации "деньги списались, но не зачислились".
- Аналитика и отчёты: SQL идеально подходит для сложных запросов, соединений (JOIN) множества таблиц и агрегации данных (SUM, AVG, GROUP BY). Это основа для построения OLAP-кубов и систем бизнес-аналитики (BI).
- Прогнозирование рисков: Современные реляционные СУБД (например, PostgreSQL) имеют мощные расширения для математических расчётов и даже машинного обучения (например, MADlib), что позволяет проводить сложный анализ и прогнозирование прямо на уровне БД.
- Зрелость и экосистема: Для финансовых систем критически важны безопасность, аудит и совместимость. SQL-системы существуют десятилетиями и имеют под собой огромное количество инструментов для защиты, резервного копирования и мониторинга.

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

Рекомендуемая СУБД:
- Для лендингов: Документоориентированная NoSQL СУБД (например, MongoDB, Couchbase).
- Для CRM: Гибридный подход. Ядро - реляционная СУБД (PostgreSQL/MySQL), а для некоторых быстро меняющихся данных - NoSQL.
Почему?
- Для лендингов:
- Гибкость: Структура данных, приходящих с форм лендинга (имя, email, телефон, выбранные опции, UTM-метки), может легко меняться. NoSQL не требует предварительного описания схемы, что позволяет быстро адаптироваться под новые требования маркетологов.
- Скорость записи: Эти СУБД оптимизированы для быстрой вставки больших объёмов данных, что важно для обработки пиковых нагрузок (например, во время рекламной кампании).
- Масштабируемость: Легко масштабируются горизонтально для обработки трафика с тысяч лендингов.
- Для CRM:
- Ядро на SQL: Основные сущности CRM (Контакты, Компании, Сделки, Задачи) имеют чёткую структуру и связи. Целостность этих данных критична для бизнеса. Реляционная СУБД идеально обеспечивает эту целостность и позволяет строить сложные отчёты по воронке продаж.
- NoSQL для гибкости: Некоторые данные, такие как история коммуникаций (логи звонков, цепочки писем, история изменений), могут иметь полуструктурированный формат. Их можно хранить в формате JSON внутри PostgreSQL или вынести в отдельную NoSQL-базу для достижения максимальной производительности и гибкости. Современные CRM часто используют гибридные модели.

1.3. База корпоративных норм, правил и обучающих материалов
Рекомендуемая СУБД:
Вариант 1 (Классический): Реляционная СУБД (например, MySQL или PostgreSQL).
Вариант 2 (Современный, набирающий популярность): СУБД типа "граф" (например, Neo4j).

Почему?
- Реляционная СУБД (Простая и понятная структура): Это надёжный и предсказуемый выбор. Правила и нормы можно организовать в виде иерархических таблиц (например, Отделы -> Процессы -> Нормы). Это легко понять, разработать и поддерживать. Отлично подходит для простого структурированного хранения.
- Графовая СУБД (Сформированная согласно структуре компании): Если структура компании сложная (матричная, с множеством взаимосвязей между отделами и проектами), графовая база данных блестяще это отобразит.
- Сущности (сотрудники, отделы, документы, нормы) становятся узлами.
- Связи между ними ("является частью", "отвечает за", "следует правилу", "ссылается на") становятся рёбрами.
- Это позволяет очень наглядно моделировать знания и делать мощные запросы: "Найти все обучающие материалы, относящиеся к нормам отдела логистики, на которые ссылаются проекты типа 'девелопмент'".
Для старта я бы рекомендовал реляционный вариант из-за его простоты. Но если задача стоит именно в моделировании связей, а не просто в хранении документов, то графовая СУБД — это более продвинутое и точное решение.

1.4. Логистика: построение маршрутов и распределение курьеров

Рекомендуемая СУБД: Графовая СУБД (например, Neo4j, Amazon Neptune).

Почему?
- "Быстрая работа со связями": Это прямая специализация графовых баз. Задачи логистики — это чистейшая форма задач теории графов.
- Узлы: Склады, объекты строительства, перекрёстки, курьеры.
- Рёбра: Дороги между точками с свойствами длина, время_проезда, стоимость_проезда, пробки.

Решаемые задачи:
- Поиск кратчайшего/оптимального пути: Стандартный алгоритм (Дейкстры) работает в графовой БД нативно и невероятно быстро, так как данные хранятся в виде связей, а не вычисляются из таблиц JOINами.
- Решение задачи коммивояжёра (TSP): Оптимальное распределение маршрутов для нескольких курьеров.
- Поиск ближайшего курьера: Запрос "найти всех свободных курьеров в радиусе 2 км от точки А" выполняется моментально.
Реляционная СУБD будет сильно проигрывать в производительности на таких задачах, так как для поиска маршрутов потребуется делать множество рекурсивных JOINов, которые "съедят" все ресурсы и будут выполняться очень медленно.

Комментраий: Не существует единой СУБД для всех задач. Правильная архитектура — это полиструктурное хранилище данных, где для каждой конкретной задачи выбирается наиболее подходящий инструмент.

## Задание 2.

1. Инициирование транзакции и проверка исходных данных
Приложение (веб-сервер или мобильный клиент) отправляет запрос в базу данных на пополнение счета. Вместо простого UPDATE всё действие заключается в транзакцию. Это критически важно.
- Что происходит: СУБД создает точку отсчета для последующих операций. Все изменения отныне будут временными, пока транзакция не будет подтверждена.
2. Проверка наличия пользователя и корректности данных
Прежде чем что-либо менять, необходимо убедиться, что пользователь с таким ID существует, его счет активен и не заблокирован. Также здесь может проверяться уникальность идентификатора платежа (чтобы избежать двойного списания).
- Что происходит: Запрос блокирует найденную запись о пользователе для других потенциальных транзакций, которые тоже хотят ее изменить. Это предотвращает состояние гонки (race condition) и гарантирует, что баланс будет вычислен корректно.
3. Зачисление средств на баланс
Если все проверки пройдены (пользователь найден, счет активен, платеж уникален), происходит основное действие – увеличение баланса.
- Что происходит: Текущее значение баланса в заблокированной строке увеличивается на сумму пополнения. Изменение пока что существует только в рамках этой транзакции.
4. Фиксация операции в журнале (логирование)
Обязательный шаг для аудита и отладки. В отдельной таблице transactions или payment_history создается запись об успешной операции.
- Что происходит: Фиксируется вся информация о платеже: кто, когда, сколько, тип операции, уникальный идентификатор платежа из внешней системы. Это "доказательство" совершения операции.
5. Фиксация транзакции (Commit)
Это самый важный шаг. До этого момента все изменения можно было отменить.
- Что происходит: СУБД применяет все изменения, сделанные в шагах 2-4 (разблокировка строки, обновление баланса, запись в лог), в основном хранилище. Транзакция завершена успешно. Баланс пользователя теперь официально увеличен.
6. Подтверждение успеха для пользовательского приложения
После успешного коммита база данных возвращает приложению подтверждение об успешном выполнении транзакции.
- Действие: Приложение получает ответ от СУБД и отображает пользователю сообщение "Баланс счёта успешно пополнен".
    
## Задание 3.

1. Четкая схема данных и целостность 
Это фундаментальное преимущество. SQL-бд требуют предварительного определения схемы: таблицы, столбцы, типы данных (INT, VARCHAR, DATE), ограничения (NOT NULL). Это обеспечивает надежность и предсказуемость данных, что в свою очередь позволяет исключить ошибки из-за неверного типа данных (например, попытка записать текст в поле даты). Встроенные механизмы (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK) гарантируют целостность связей и логическую правильность данных на уровне бд. В NoSQL валидация данных часто ложится на приложение, что повышает риски появления ошибок в данных.
2. Мощный и стандартизированный язык запросов (SQL)
SQL — это единый, стандартизированный, декларативный язык для работы с данными. Вы описываете что вам нужно, а не как это получить. Благодаря этому один SQL-запрос с JOIN и агрегирующими функциями (SUM, COUNT, GROUP BY) может заменить сотни строк итерационного кода в приложении для NoSQL-БД. Сложная аналитика и выборка из множества связанных таблиц — сильная сторона SQL.
3. Транзакции, обеспечивающие атомарность (ACID-транзакции)
Полная поддержка ACID  — краеугольный камень реляционных БД. Группа операций выполняется как единое целое (транзакция). Либо все операции одобрены, либо ни одной. Это критически важно для финансовых операций, банковских переводов, систем бронирования. Многие NoSQL-системы жертвуют строгой консистентностью или атомарностью в распределенных сценариях в пользу доступности и скорости.
4. Связи между данными и устранение избыточности
Данные хранятся в нормализованном виде (без дублирования) в разных таблицах и связываются через внешние ключи (FOREIGN KEY). В результате этого исключается аномалия обновления/удаления. Чтобы изменить адрес пользователя, его меняют только в одном месте (в таблице users), а не в каждой его записи заказа (как это могло бы быть в документной NoSQL-БД). Это экономит место и гарантирует консистентность.
5. Зрелость, надежность и сообщество
Реляционные СУБД (на пример PostgreSQL, MySQL) существуют десятилетия, они тщательно протестированы, отлажены и имеют огромное сообщество. Данное преимущество приводит к предсказуемости, стабильности, наличию обширной документации, множеству инструментов для администрирования, бэкапа, мониторинга. Опытных SQL-администраторов и разработчиков найти значительно проще. Риск нарваться на "сырую" или нишевую технологию ниже.

## Задание 4.

Критерий выбора типа СУБД
Ключевой критерий, на котором будет основан выбор — характер данных и природа вычислений. Прежде чем выбирать инструмент, нужно понять задачу:
1. Структурированные vs. Неструктурированные данные:
- Структурированные: Данные имеют четкую схему (например, таблицы с строгими типами полей: user_id INT, transaction_date DATETIME). Вычисления носят аналитический характер (агрегации, JOIN, сложные фильтры). Пример: расчет итоговой выручки по регионам за последний квартал.
- Неструктурированные/Полуструктурированные: Данные представляют собой документы (JSON, XML), графы, ключ-значение пары. Вычисления часто связаны с обработкой всего документа, машинным обучением или анализом связей. Пример: анализ тональности текстовых логов или рекомендации на основе графа взаимодействий пользователей.
2. Тип вычислительной нагрузки:
- OLAP (Online Analytical Processing): Задачи, требующие полного сканирования огромных объемов данных для агрегации и анализа. Это "тяжелые" запросы, которые читают почти все строки в таблице, но выполняются относительно редко.
- OLTP (Online Transaction Processing): Задачи, требующие быстрых точечных операций (вставка, обновление, поиск по ключу) над небольшими порциями данных. Высокая частота операций.
Вердикт: Условие "огромное количество данных" и "большое количество вычислений" с кластером в 1000 машин — это классический признак OLAP-задачи (аналитика, Data Mining, отчетность). Следовательно, мы будем рассматривать либо колоночные SQL-СУБД, либо MapReduce-подобные системы из BigData-стека (NoSQL).

Модель распределенных вычислений
Лучше всего с этой задачей справится модель MapReduce (или её более современные и эффективные реализации, такие как Apache Spark).
Почему именно она?
1. Масштабируемость "из коробки": Модель MapReduce была разработана именно для обработки петабайтов данных на тысячах commodity-машин. Её архитектура идеально подходит для горизонтального масштабирования. Добавление новой машины в кластер линейно увеличивает вычислительную мощность и объем хранилища.
2. Отказоустойчивость: Одна из ключевых проблем большого кластера — ненадежность железа. Вероятность выхода из строя хотя бы одной машины из 1000 в любой момент времени очень высока. MapReduce-фреймворки (Hadoop, Spark) автоматически обрабатывают сбои. Если упала задача на одной машине, она автоматически перезапускается на другой. Пользователь и администратор не замечают этого.
3. Локальность данных (Data Locality): Фреймворк стремится обрабатывать данные там, где они хранятся. Вместо того чтобы гонять Terabytes данных по сети, код (задача Map) отправляется на машину, где находятся нужные данные. Это кардинально снижает нагрузку на сеть — главное узкое место в распределенных системах.
4. Простота программирования: Модель Map -> Shuffle -> Reduce предоставляет простой и мощный абстракктный уровень для программиста. Не нужно думать о распараллеливании, распределении данных, синхронизации и обработке сбоев. Нужно лишь описать две функции: map и reduce. Всю "грязную" работу по оркестрации этих функций на тысяче машин берет на себя фреймворк (например, YARN в Hadoop).
5. Принцип решения:
- Map (Фаза отображения): Большая задача разбивается на множество мелких подзадач. Каждая машина в кластере обрабатывает (map) свой небольшой кусок входных данных независимо и параллельно.
- Shuffle (Фаза перемешивания): Промежуточные результаты сортируются и распределяются между машинами для следующего этапа.
- Reduce (Фаза свертки): Машины агрегируют (reduce) полученные промежуточные результаты, чтобы получить итоговый ответ.
Эта модель идеально ложится на задачи типа "посчитать среднее", "найти максимум", "сгруппировать по", "построить индекс".

Практическая рекомендация
Для такой задачи я бы рекомендовал использовать современный стэк на основе Apache Spark, развернутый поверх кластера.
- Почему Spark, а не классический Hadoop MapReduce? Spark выполняет вычисления в оперативной памяти (in-memory), что на порядки (в 10-100 раз) быстрее для итеративных алгоритмов (машинное обучение) и интерактивных запросов, чем Hadoop, который постоянно пишет на диск.
- Где хранятся данные? В качестве распределенной файловой системы или хранилища данных используется HDFS (Hadoop Distributed File System) или облачные аналоги (S3, GCS). Данные надежно распределены и реплицированы по всем узлам кластера.
- Что насчет СУБД? Если данные изначально структурированы и требуют сложных запросов с JOIN, поверх Spark можно использовать колоночную СУБД типа Apache Hive или ClickHouse. Они преобразуют SQL-запросы в набор заданий MapReduce/Spark, сочетая удобство SQL с мощью распределенных вычислений.
Итог: Критерий выбора — OLAP-нагрузка на больших данных. Лучшая модель — MapReduce/Spark, так как она обеспечивает линейное масштабирование, отказоустойчивость и эффективное использование ресурсов большого кластера.
