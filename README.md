# Решение

## Задание 1
1.1. Восстановление данных в полном объёме за предыдущий день

Подходящий вариант: Полное резервное копирование, выполняемое ежедневно.

Обоснование:
   - Полный бэкап содержит все данные на момент создания копии.
   - Позволяет восстановить всю БД на состояние конца предыдущего дня.
   - Простота восстановления: нужна только одна резервная копия.
   - Рекомендуется дополнять логическими резервными копиями для возможности восстановления отдельных объектов.

1.2. Восстановление данных за час до предполагаемой поломки

Подходящий вариант: Комбинированная стратегия: Полное + Инкрементное/Дифференциальное + Резервное копирование журналов транзакций (WAL в PostgreSQL, binlog в MySQL)

Обоснование:
   - Полный бэкап (еженедельно) - базовая точка восстановления.
   - Инкрементный/дифференциальный бэкап (ежедневно) - копии изменений с последнего полного/инкрементного бэкапа.
   - Копирование журналов транзакций (каждый час/непрерывно) - позволяет восстановить данные до конкретного момента времени (Point-in-Time Recovery, PITR).
   - Для восстановления за час до поломки потребуется: последний полный бэкап + все инкрементные копии до нужного дня + журналы транзакций за последний день до нужного момента.



## Задание 2
2.1. Пример команд резервирования и восстановления БД

Резервное копирование с помощью pg_dump:
Команды:

### Полное резервное копирование базы в custom формате (сжатый)
pg_dump -U username -d database_name -F c -f /path/to/backup/backup_file.dump -v

### Полное резервное копирование в SQL-формате
pg_dump -U username -d database_name -F p -f /path/to/backup/backup_file.sql

### Резервное копирование всего кластера (всех БД)
pg_dumpall -U username -f /path/to/backup/full_backup.sql

Восстановление с помощью pg_restore:
Команды:

### Восстановление в новую базу данных
pg_restore -U username -d new_database_name -v /path/to/backup/backup_file.dump

### Восстановление только структуры (без данных)
pg_restore -U username -d database_name --schema-only /path/to/backup/backup_file.dump

### Восстановление с использованием параллельных потоков (ускорение)
pg_restore -U username -d database_name -j 4 -v /path/to/backup/backup_file.dump

Для Point-in-Time Recovery (PITR) необходимо:

Активировать архивацию WAL в postgresql.conf:
Содержание конфигурационного файла:

wal_level = replica
archive_mode = on
archive_command = 'cp %p /path/to/wal_archive/%f'

Выполнять базовые резервные копии с помощью pg_basebackup:
Команда:
pg_basebackup -D /path/to/backup/base -Ft -z -U replication_user


## Задание 3
3.1. Пример инкрементного резервного копирования
Для использования инкрементного бэкапа требуется активировать бинарное логирование:

В конфигурации MySQL (my.cnf/my.ini):

ini

[mysqld]
log-bin = /var/log/mysql/mysql-bin.log
server-id = 1

Выполнение инкрементного резервного копирования с помощью mysqlbinlog:

Полный бэкап (воскресенье):

mysqldump -u root -p --single-transaction --flush-logs \
--master-data=2 --all-databases > /backup/full_backup_$(date +%Y%m%d).sql

Инкрементные бэкапы (понедельник-суббота):

### После полного бэкапа выполнять ежедневно
mysqladmin -u root -p flush-logs

### Копирование бинарных логов (инкрементные изменения)
cp /var/log/mysql/mysql-bin.00000* /backup/incremental/

Пример восстановления из инкрементного бэкапа:

### Восстановление полного бэкапа
mysql -u root -p < /backup/full_backup_20240101.sql

### Восстановление инкрементных изменений (последовательно)
mysqlbinlog /backup/incremental/mysql-bin.000002 | mysql -u root -p
mysqlbinlog /backup/incremental/mysql-bin.000003 | mysql -u root -p
