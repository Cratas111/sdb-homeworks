# Решение

## Задание 1
Преимущества различных методов масштабирования:
1. Активный master-сервер и пассивный репликационный slave-сервер

Основные преимущества:

    Разделение нагрузки: Master обрабатывает операции записи, slave - только чтение
    Увеличение отказоустойчивости: При падении master-сервера slave может быть переведен в режим master
    Безопасность: Slave можно использовать для резервного копирования без влияния на производительность master
    Тестирование и аналитика: На slave можно выполнять тяжелые запросы отчетов и аналитики без нагрузки на master
    Простота настройки: Минимальная конфигурация с одним slave проще в управлении

Пример использования:
Блог-платформа, где master обрабатывает публикации новых постов (запись), а slave обслуживает читателей (чтение).
2. Master-сервер и несколько slave-серверов

Основные преимущества:
    Масштабирование чтения: Нагрузка на чтение распределяется между несколькими slave-серверами
    Географическое распределение: Slave-серверы могут располагаться в разных регионах для уменьшения задержки
    Высокая доступность: При выходе из строя одного slave-сервера другие продолжают обслуживать запросы
    Специализация slave-серверов:
        Один slave - для аналитических запросов
        Другой - для оперативной информации
        Третий - для резервного копирования

    Постепенное масштабирование: Можно добавлять slave-серверы по мере роста нагрузки

Пример использования:
Социальная сеть с одним master для обновлений профилей и несколькими slave-серверами для отображения ленты новостей в разных регионах.



## Задание 2
1. Принципы вертикального и горизонтального шардинга

Вертикальный шардинг

Разделение по функциональным модулям.
Каждый шард = отдельная логическая область системы.

Принцип

Мы разделяем данные по "типу":
Пользователи — в одной БД
Книги — в другой БД
Магазины — в третьей БД

Это даёт:

Независимую масштабируемость для пользователей, книг, магазинов
разные режимы работы БД (например, только чтение, репликации, кеширование)

Горизонтальный шардинг 
Разделение строк одной таблицы между разными серверами.

Принцип
Например, таблица пользователи может быть разделена по диапазону user_id:

Shard 1 → user_id 1–1 000 000
Shard 2 → user_id 1 000 001–2 000 000

Таблица книги может быть разделена по категории:

Художественная литература → Shard A
Учебники → Shard B
Комиксы → Shard C

Таблица магазины может быть разделена по географическому признаку:

Europe → Shard EU
Asia → Shard APAC
America → Shard US

2. План разработки шардинга
Этап 1 — Вертикальный шардинг - функциональное разделение
3 отдельные БД:

БД 1: users_db

Хранит:

users
Может работать в режиме:
мастер - запись
2–3 слейва - чтение

БД 2: books_db

Хранит:

books
Может работать в режиме:
master - запись
slave - быстрый поиск, API каталога книг

БД 3: stores_db

Хранит:

stores
Может работать в режиме:
только мастер (если низкая нагрузка)
Или
master + slave для аналитики

Этап 2 — Горизонтальный шардинг (масштабирование по строкам)
Пользователи — шардирование по диапазону user_id

users_db_shard_1
user_id 1–1M

users_db_shard_2
user_id 1M–2M
users_db_shard_N

и так далее

Механизм выбора шарда может быть:

по user_id (range-based)
или по хэшированию (hash(user_id) % N)

Книги — шардирование по тематике/типу (category-based)

books_shard_1 – Fiction
books_shard_2 – Education
books_shard_3 – Comics
books_shard_4 – Other

Магазины — географическое шардирование

stores_shard_eu – Европа
stores_shard_us – Америка
stores_shard_apac – Азия

Этап 3 — Репликация

Каждый шард имеет:

master — обработка записей
slave — чтение, аналитика, масштабирование

Режимы MySQL:

Master - принимающий изменения
Slave - Replica_IO_Running + Replica_SQL_Running

Этап 4 — Сервис маршрутизации запросов (Query Router)

Нужен отдельный уровень:

Router-service выполняет:
Определяет, к какому шарду обратиться. Определяет, читать или писать. Перенаправляет запрос к:
master (если INSERT/UPDATE/DELETE)
slave (если SELECT)

Это может быть:

Свой сервис (Node.js / Go)

ProxySQL
MySQL Router
